# Хранилище документации: подключаемые провайдеры БД

## Статус: реализовано

Документация теперь может храниться либо локально (SQLite, по умолчанию), либо во внешней
базе PostgreSQL. Добавление любого другого провайдера в будущем сводится к реализации
`IDocumentStore` и одной новой ветке выбора в `DatabaseService` — без изменений в UI,
вьюмоделях или тестах.

## Архитектура

- `IDocumentStore` (`Storage/IDocumentStore.cs`) — контракт хранилища: дерево документов,
  содержимое, версии, вложения, статусы, теги, свойства, поиск (~55 членов).
- `SqliteDocumentStore` (`Storage/SqliteDocumentStore.cs`) — провайдер по умолчанию,
  извлечён из прежнего `DatabaseService` без изменения логики; путь к файлу БД настраивается
  через конструктор.
- `PostgresDocumentStore` (`Storage/PostgresDocumentStore.cs`) — новый провайдер на Npgsql.
  Ключевые переводы диалекта задокументированы в комментарии к классу: `AUTOINCREMENT` →
  `GENERATED ALWAYS AS IDENTITY` + `RETURNING Id`; GUID генерируются в C# / выражением
  `md5(...)::uuid` (без расширений); `COLLATE NOCASE` → тип `CITEXT` (или `TEXT`, если
  расширение недоступно) для Title/Statuses.Name/Tags.Name; FTS5 → `tsvector`/GIN-индекс +
  `ts_rank_cd`/`ts_headline` с теми же маркерами подсветки `⟦`/`⟧`; `group_concat` →
  `string_agg`. Точность полнотекстового ранжирования и работоспособность SQL стоит
  проверить на реальном сервере PostgreSQL — в этой среде нет доступа к `dotnet`/серверу БД
  для компиляции и прогона.
- `PostgresProvisioning` (`Storage/PostgresProvisioning.cs`) — автосоздание внешней базы:
  если базы из строки подключения ещё нет (`SqlState 3D000`), она создаётся через служебную
  базу `postgres`/`template1` под теми же учётными данными (нужно право `CREATEDB`).
  Расширение `citext` ставится, если позволяют права; при отказе схема создаётся на `TEXT`
  (регистронезависимость названий теряется, но всё остальное работает). GUID генерируются
  на стороне C# либо выражением `md5(...)::uuid`, поэтому `pgcrypto` и `gen_random_uuid()`
  не требуются. `RefreshTypeCache` вызывается в конце `Initialize`: Npgsql читает каталог типов
  один раз при первом подключении и кеширует его глобально, поэтому созданный позже тип `citext`
  оставался клиенту неизвестным и первое же чтение `Nodes.Title` падало с `InvalidCastException`
  («…fields having DataTypeName '.&lt;unknown&gt;'»).
- `PostgresErrorInfo` (`Storage/PostgresErrorInfo.cs`) — расшифровка ошибок для интерфейса:
  короткая строка для полосы состояния и подробное описание (причина, что сделать, код SqlState,
  деталь/подсказка сервера, таблица и колонка) для диалога.
- `DatabaseService` (`Storage/DatabaseService.cs`) — тонкий фасад: публичное имя и API не
  изменились, поэтому ни один из ~12 мест использования в App/Backup/тестах не потребовал
  правок. Внутри выбирает `SqliteDocumentStore` или `PostgresDocumentStore` по сохранённой
  конфигурации; если выбран Postgres, но подключиться не удалось — откатывается на SQLite и
  пишет причину в журнал.
- `StorageProviderConfig` / `StorageConfigService` (`Storage/StorageProviderConfig.cs`,
  `Storage/StorageConfigService.cs`) — выбор провайдера и строка подключения к Postgres
  хранятся в `storage-provider.json` рядом с `data-location.txt`, чтобы быть читаемыми до
  создания DI-контейнера. `StorageConfigService.TestConnection` проверяет соединение без
  изменения активной конфигурации.
- `LocalStateService` (`Storage/LocalStateService.cs`) — состояние интерфейса рабочего места
  (размеры и положение окна, ширины панелей, раскрытые узлы дерева, дата автокопии) хранится
  в локальном `ui-state.json`, а не в базе. В общей базе — только документация: страницы,
  папки, изображения и вложения, теги, статусы, свойства, версии. Таблица `Settings` из схемы
  PostgreSQL удалена (и удаляется из уже созданных баз при инициализации); из локального
  SQLite прежние значения один раз переносятся в файл, чтобы не потерять раскладку окна.
  Настройки приложения (тема, шрифты, горячие клавиши) как и раньше живут в `settings.json`.
## Таблицы базы данных

| Таблица | Что хранит |
| --- | --- |
| `nodes` | Дерево документации: и папки, и страницы (`IsFolder`). Для страницы — всё её содержимое: `EditorJson` (то, из чего редактор рисует страницу), `Html`, `Markdown`, `PlainText`, старый формат `Content` (XamlPackage), а также `Title`, `ParentId`, `SortOrder`, даты, `Status`, `IsFavorite`, `IsTemplate`, `Zoom`, `Guid` (постоянная ссылка на страницу), `Author`, `IsPrivate`/`Owner` (приватные страницы видит только владелец) и `DeletedAt` (корзина). |
| `assets` | Двоичное содержимое изображений и вложений: `StoredName` (имя по SHA-256), `Data BYTEA`, `MimeType`, `Size`. Один и тот же файл хранится одной строкой независимо от того, сколько страниц на него ссылаются. |
| `attachments` | Список вложений страницы: исходное имя файла, `StoredName` (ссылка на `assets`), тип, размер, хеш, дата. Сам файл лежит в `assets`. |
| `tags` | Справочник тегов (уникальные названия). |
| `documenttags` | Связка «страница ↔ тег». |
| `statuses` | Справочник статусов документа («Черновик», «В работе», …), порядок сортировки и признак встроенного. |
| `customproperties` | Пользовательские свойства страницы: пара «название — значение». |
| `documentversions` | История версий страницы: снимок содержимого при каждом сохранении, причина, размер, признак «закреплена». Хранится до 100 незакреплённых версий на страницу. |
| `searchindex` | Полнотекстовый индекс: заголовок, текст страницы вместе со статусом, названием родительской папки, тегами и именами вложений, плюс `tsvector` с GIN-индексом. Служебная таблица, восстанавливается кнопкой «Перестроить поисковый индекс». |
| `schemamigrations` | Номер версии схемы и дата применения. Служебная. |

Состояния интерфейса, темы и настроек приложения в базе нет — только документация.

## Изображения и вложения

Файлы никуда на файловую систему сервера не кладутся: содержимое хранится прямо в базе
(таблица `assets`, колонка `Data BYTEA`, ключ — имя файла по SHA-256). Никаких папок на сервере
и прав на диск не нужно — достаточно обычных прав на запись в таблицу. Локальная папка `Assets`
на машине пользователя — только кэш, из которого редактор отдаёт картинку по адресу
`https://assets.local/<имя>`; недостающие файлы выгружаются из базы при открытии страницы.

Одинаковый рисунок, выгруженный несколькими людьми, остаётся в базе одной строкой (ключ по
SHA-256 + `ON CONFLICT`). Если файл не удалось записать (например, у пользователя нет прав на
таблицу `assets`), перенос не прерывается: сбойные файлы попадают в `MigrationReport`,
пользователю показывается подробный отчёт, а в интерфейсе появляется кнопка «Повторить перенос
изображений» — она везёт только файлы, документацию заново не копирует.

## Повторный перенос

Перенос идемпотентен. Страница узнаётся по постоянному идентификатору `Nodes.Guid`:

- страница уже есть в целевой базе → обновляется на месте (содержимое, статус, теги, свойства,
  масштаб, приватность), новая версия попадает в `documentversions`;
- страницы нет → создаётся, и ей присваивается идентификатор оригинала (`SetDocumentGuid`),
  поэтому следующая выгрузка снова обновит её, а не задвоит. Связь работает и в обратную
  сторону: импортированная к себе страница при выгрузке вернётся в ту же строку базы;
- вложения регистрируются только те, которых у страницы ещё нет (сравнение по `StoredName`),
  поэтому список вложений не разрастается копиями;
- файлы в `assets` адресуются по SHA-256 и переписываются `ON CONFLICT DO UPDATE`.

## Одновременная работа нескольких пользователей

- уникальный индекс `IX_Nodes_Sibling_Kind` (`COALESCE(ParentId,0)`, `IsFolder`, `lower(Title)`,
  только не удалённые) не даёт задвоить элемент, если два человека создают одинаковое название
  одновременно. `IsFolder` входит в ключ: папка и документ — разные типы элементов и одинаковое
  название в одной папке допустимо, запрещены только два документа или две папки с одним названием;
  `Create` превращает отказ базы в обычную ошибку «такой элемент уже существует»;
- перенос переиспользует уже существующую папку, а для документа подбирает следующее свободное
  название вместо падения;
- ошибка на одной странице не обрывает перенос: она попадает в отчёт, остальные страницы едут дальше;
- поисковый индекс обновляется upsert-ом, а не `DELETE` всей таблицы, поэтому одновременные
  переносы не блокируют друг друга и не оставляют соседям пустой поиск;
- связки документ-тег вставляются с `ON CONFLICT DO NOTHING`, файлы — с `ON CONFLICT DO UPDATE`.

- `StorageMigrationService` (`Storage/StorageMigrationService.cs`) — перенос дерева
  документов, содержимого, тегов, свойств, вложений (метаданных), избранного и шаблонов
  между двумя произвольными реализациями `IDocumentStore`. История версий и общий реестр
  `Settings` (ключ-значение) при переносе не копируются — это осознанное ограничение
  (IDocumentStore не даёт перечислить все ключи Settings разом).

## Пакеты

`MasterDocumentation.Infrastructure.csproj`: добавлены `Npgsql 8.0.3` и `Dapper 2.1.35`
(Dapper подключён для будущих удобных запросов; основная реализация использует Npgsql
напрямую — построчный перенос SQLite-кода был признан менее рискованным без возможности
компиляции в этой среде).

## Настройки (UI)

В `Настройки → Хранение` добавлен блок «База данных»:
- переключатель SQLite / PostgreSQL;
- поле строки подключения Npgsql (видно только при выборе PostgreSQL);
- кнопка «Проверить соединение» (`StorageConfigService.TestConnection`, не меняет
  сохранённые настройки);
- кнопка «Перенести текущие данные в PostgreSQL» (`StorageMigrationService.CopyAll` в
  фоновом потоке, с индикацией прогресса).

Готовить схему вручную не нужно: и при переносе, и при обычном запуске с выбранным
PostgreSQL приложение само создаёт базу данных, расширения, таблицы и индексы
(`PostgresProvisioning.EnsureDatabase` + `PostgresDocumentStore.Initialize`). Достаточно
указать строку подключения; несуществующая база в проверке соединения показывается как
«будет создана автоматически», а не как ошибка. Минимальные требования к серверу —
PostgreSQL 12+ (generated-колонка `tsvector`) и право `CREATEDB` у пользователя (если базы
ещё нет).

Выбор провайдера сохраняется в `storage-provider.json` при нажатии «Сохранить» и
применяется после перезапуска приложения (пользователь предупреждается диалогом).

## Резервное копирование

`BackupService` определяет активный провайдер через `StorageConfigService.Load()`:
- SQLite → как раньше, копия файла БД + `Assets` в `.mdbackup`;
- любой другой провайдер → «логическая» копия: дерево документов выгружается через
  `IDocumentStore` в `logical-dump.json` внутри того же `.mdbackup` (плюс `Assets`).
  Логическую копию можно восстановить в ЛЮБОЙ активный на момент восстановления провайдер —
  она не привязана к конкретной СУБД, в отличие от файловой копии SQLite.
- При попытке восстановить файловую (SQLite) копию, когда активен не-SQLite провайдер,
  `Restore` бросает понятную ошибку вместо тихой порчи данных.

## Известные ограничения / что стоит проверить на реальном Postgres

1. Компиляция и фактический прогон против PostgreSQL не выполнялись — в этой среде нет
   `dotnet` SDK и доступа к серверу БД. Весь код проверен вычиткой (Read/Grep), включая
   сверку соответствия всех членов `IDocumentStore` во всех трёх реализациях.
2. Перевод полнотекстового поиска (FTS5 → tsvector) — рабочий, но приближённый; ранжирование
   `ts_rank_cd` не идентично `bm25`.
3. `Checkpoint()`/`CheckIntegrity()` для Postgres — best-effort (обычный пользователь БД может
   не иметь прав на `CHECKPOINT`; ошибка в этом случае тихо игнорируется).
4. Перенос данных и логические резервные копии не включают историю версий документов и
   общие настройки Settings (ключ-значение).
